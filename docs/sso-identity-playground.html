SSO Build Identity Explorer

Why Google sign-in works on a laptop, fails in QA, and would fail in production — Sefaria Mobile.

One idea explains everything on this page.

Every app build has an identity. Google and Apple only let a build sign users in if that exact identity was registered with them in advance.

📱 Android identity = applicationId + SHA-1 fingerprint. The app carries no client id — Google recognises it by that pair alone.

🍎 iOS identity = bundle id only. No certificate involved — but the app does carry a client id, in Info.plist.

3 · Production is broken too — the highest-priority finding 🔴

This is not the QA symptom that started the investigation. It is latent, and it would hit every real user.

Reason A · Play re-signs your app

You upload a build signed with the upload key. Google Play strips that signature and re-signs with its own app signing key.

So users run a build whose fingerprint was never registered. You must register the App signing key certificate from Play Console → App Integrity — not just the upload key. Registering only the upload key is the classic cause of “works everywhere except from the Play Store”.

Reason B · No client id in any CI build

.env is gitignored, and until commit f2efdf4f no workflow created one.

So serverClientId — the web client id the SDK needs — was undefined in every QA and production build. Two independent gaps, stacked; both must close.

6 · Separate security item 🔓

react-native-config publishes every key in .env into both BuildConfig and an APK string resource — plain, extractable text.

So APPLE_SSO_PRIVATE_KEY is readable in any locally built APK. CI builds are clean: they write only the Google client id.

Those keys are backend settings (sefaria/local_settings.py) that were copied into the mobile repo by mistake. Nothing in the app reads them. Delete them; rotate only if a locally built APK was ever shared.
